# zen of zaal
- simple abstraction / minimal implementaion.
  - runtime should be very small.
- avoid adding millions of features that do the same things but in different ways!
- in zaal, we have only two entities. functions or data.
  - functions are the last layer of abstraction.
  - you should add metadata to them, which allows compiler knows what are their behaviour/features at compile/run time.
- zaal compiler is stuipd, which means:
  - you need to tell him everything you need. (through metadata mechanism)
  - we tried to use less "inference" as much as we can.
- it's also very strict, which means:
  - it tries to catches the errors at compile-time as much as it can.

# you don't see these things in zaal
- gc
- macro
- alias
- template
- type punning
- namespaces. instead we have modules. (each file is a module)
- possiblity to link against c/c++ code/libraries or any other programming langauge.
- dynamic libraries:
  - all the libraries and binaries should statically build.
- OO:
  - no operator overloading.
  - no polymorphism.
  - no inheritance.
    - this encourage users to use composition over inheritance.
- exceptions:
  - zaal relies on metadata.outputArgs:
    outputArgs: [ 
      {
        name: status,
        type: bool,
        allocatedOn: stack,
        immutable: false
      },
      {
        name: message,
        type: string,
        allocatedOn: stack,
        immutable: false
      }
    - these are mandatory for each function. it means you need to define it as part of your function definition -> otherwise compiler error.
